# Redis持久化：RDB与AOF机制对比分析

## 前言

Redis的高性能得益于其将数据存储在内存中，但内存中的数据在进程退出后会丢失。为了保证数据的持久性，Redis提供了两种持久化机制：RDB和AOF。本文将深入分析这两种持久化机制的工作原理、配置选项、以及各自的优缺点，帮助读者在实际生产环境中做出合适的选择。

## 持久化概述

### 为什么需要持久化？

```
┌─────────────┐      ┌─────────────┐
│   Memory    │ ───> │   Disk      │
│   (RAM)     │      │   (SSD/HDD) │
└─────────────┘      └─────────────┘
    高速读写             持久存储
    易失性              持久性
```

- **内存**：读写速度极快（纳秒级），但断电后数据丢失
- **磁盘**：读写速度较慢（微秒级），但数据持久化

Redis的定位是高性能缓存，但很多场景需要持久化存储。

## 1. RDB（Redis Database）

### 工作原理

RDB是Redis默认的持久化方式，它会在特定的时间点生成数据集的快照（Snapshot）。

```
触发时机：
├── 定时触发（BGSAVE）
├── 客户端命令（SAVE、BGSAVE）
├── 配置文件规则
└── 主从复制（从节点）
```

### 触发机制

#### 1. SAVE命令（同步阻塞）

```bash
# 阻塞Redis服务器，直到RDB文件创建完成
# 不推荐在生产环境使用
SAVE
```

**执行流程**：
```
主进程执行SAVE：
1. 阻塞所有客户端请求
2. 调用fork()创建子进程
3. 子进程遍历内存，生成RDB文件
4. 完成前通知主进程
5. 恢复服务
```

#### 2. BGSAVE命令（异步非阻塞）

```bash
# 后台异步生成RDB快照
BGSAVE
# 客户端可继续处理其他请求
```

**执行流程**：
```
1. 客户端执行BGSAVE
2. Redis fork()创建子进程（fork是Copy-On-Write）
3. 子进程遍历内存，生成RDB文件
4. 主进程继续处理请求
5. 子进程完成后发送信号给主进程
```

#### 3. 配置文件自动触发

```conf
# 配置示例
save 900 1      # 900秒内至少1个key变化则触发
save 300 10     # 300秒内至少10个key变化则触发
save 60 10000   # 60秒内至少10000个key变化则触发

# 默认配置
save 900 1
save 300 10
save 60 10000
```

#### 4. SHUTDOWN命令

```bash
# Redis服务关闭时，如果没有开启AOF，会自动执行RDB
redis-cli shutdown
```

### RDB文件结构

```
┌────────┬────────┬────────┬────────┬─────────┐
│ MAGIC  │ 版本号 │  数据库 │  EOF   │ CRC64   │
│ REDIS  │ 0007   │ 0~15   │  0xFF  │ 校验码  │
└────────┴────────┴────────┴────────┴─────────┘

数据库区域：
┌────────────┐
│ SELECT DB  │  数据库号码
│ key-value │  键值对
│ key-value │
│  ...      │
└────────────┘
```

### RDB优缺点

#### 优点

```markdown
1. 文件紧凑，适合备份
   - 全量数据，文件较小
   - 可以快速传输到其他服务器

2. 恢复速度快
   - 只需加载一个文件
   - 对于数据恢复场景非常高效

3. 主进程不阻塞
   - BGSAVE使用Copy-On-Write
   - 不会影响客户端请求

4. 适合灾难恢复
   - 可以定期上传到远程存储
```

#### 缺点

```markdown
1. 数据可能丢失
   - 上次快照之后的数据会丢失
   - 取决于触发频率设置

2. fork()开销
   - 数据集大时，fork()耗时增加
   - Copy-On-Write期间内存翻倍风险

3. 无法实时持久化
   - 不适合对数据完整性要求极高的场景
```

### 配置参数

```conf
# RDB文件名
dbfilename dump.rdb

# RDB文件存放目录
dir /var/lib/redis

# 是否压缩RDB文件
rdbcompression yes

# 保存时是否使用RC64校验
rdbchecksum yes

# 如果开启AOF，RDB是否继续保存
stop-writes-on-bgsave-error yes

# 自动触发规则（可禁用自动触发）
# save ""
```

## 2. AOF（Append Only File）

### 工作原理

AOF通过记录所有写命令来持久化数据，类似于MySQL的binlog。

```
写操作流程：
┌────────┐    写命令    ┌─────────┐    同步    ┌────────┐
│ Client │ ---------> │ Redis   │ --------> │ AOF文件 │
└────────┘            └─────────┘            └────────┘
                      内存数据                  追加写入
```

### AOF同步策略

```conf
# 配置项：appendfsync
# 三种策略可选
```

| 策略 | 说明 | 安全性 | 性能 |
|---|---|---|---|
| **always** | 每个写命令都同步 | 最高 | 最差 |
| **everysec** | 每秒同步一次（默认） | 中等 | 较好 |
| **no** | 由操作系统决定 | 最低 | 最好 |

#### 1. always

```conf
appendfsync always
# 每个写操作都同步到磁盘
# 最多丢失一个写命令
# 对性能影响较大，不推荐
```

#### 2. everysec（推荐）

```conf
appendfsync everysec
# 每秒调用一次fsync
# 最多丢失1秒的数据
# 性能和安全性的平衡
```

#### 3. no

```conf
appendfsync no
# 不主动同步，由操作系统决定
# 通常30秒左右同步一次
# 性能最好，但可能丢失较多数据
```

### AOF重写机制

#### 为什么需要重写？

```bash
# 假设执行了以下操作：
SET counter 0        # 写入
INCR counter         # +1
INCR counter         # +1
INCR counter         # +1
DECR counter         # -1
DECR counter         # -1

# AOF文件中记录了6条命令
# 但实际上只需要一条：SET counter -1
```

#### 重写原理

```c
// AOF重写会创建一个新的AOF文件
// 包含重建当前数据集所需的最少命令

// 1. fork子进程
// 2. 子进程遍历内存，生成新数据集的最小命令
// 3. 父进程继续处理请求，同时将新命令写入两个文件
// 4. 子进程完成重写，通知父进程
// 5. 父进程将缓冲区中的命令追加到新AOF文件
// 6. 原子替换旧的AOF文件
```

#### 触发机制

```conf
# 自动重写配置
auto-aof-rewrite-percentage 100  # 文件大小超过上次重写后的100%时触发
auto-aof-rewrite-min-size 64mb  # 文件至少达到64MB才触发重写
```

```bash
# 也可以手动触发
BGREWRITEAOF
```

#### 重写缓冲区

```
┌──────────────────────────────────────────────────┐
│                    AOF重写                       │
├──────────────────────────────────────────────────┤
│                                                  │
│  主进程：                                         │
│  ├─> 继续接收请求                                 │
│  ├─> 写入旧AOF文件                                │
│  └─> 写入AOF重写缓冲区                             │
│                                                  │
│  子进程：                                         │
│  └─> 读取内存，生成新AOF文件                      │
│                                                  │
│  重写完成：                                       │
│  └─> 将AOF重写缓冲区内容追加到新AOF文件           │
│      原子替换旧AOF文件                            │
└──────────────────────────────────────────────────┘
```

### AOF优缺点

#### 优点

```markdown
1. 数据安全性更高
   - 支持多种同步策略
   - everysec策略最多丢失1秒数据

2. 写入格式易理解
   - AOF文件是追加的命令序列
   - 可以手动编辑（不推荐）

3. 后台重写机制
   - BGREWRITEAOF不会阻塞
   - 自动重写控制文件大小

4. 更好兼容性
   - 某些场景下可用AOF恢复数据
```

#### 缺点

```markdown
1. 文件通常比RDB大
   - 包含所有写命令
   - 存在冗余命令

2. 恢复速度可能较慢
   - 需要逐条执行命令
   - 对于大规模数据集

3. 可能存在bug
   - AOF写入可能被截断
   - Redis 7.0引入multi-part AOF解决
```

### AOF配置

```conf
# 开启AOF
appendonly yes

# AOF文件名
appendfilename "appendonly.aof"

# 同步策略
appendfsync everysec

# AOF重写配置
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

# 是否加载不完整的AOF
aof-load-truncated yes

# 开启RDB+AOF混合持久化
aof-use-rdb-preamble yes
```

## 3. 混合持久化（Redis 4.0+）

### 工作原理

```conf
# 开启混合持久化
aof-use-rdb-preamble yes
```

```
┌────────────────────────────────────────────────────┐
│                  混合AOF文件                        │
├────────────────────────────────────────────────────┤
│  RDB格式   │  AOF格式                               │
│  (二进制)  │  (命令序列)                            │
│            │  "SET key value"                      │
│  前部分是RDB│  "INCR counter"                        │
│  快照       │  ...                                  │
└────────────────────────────────────────────────────┘
```

### 优势

```markdown
1. 快速恢复
   - RDB部分提供快速加载
   - AOF部分记录增量修改

2. 文件紧凑
   - 利用RDB压缩
   - 避免AOF膨胀

3. 兼容性
   - 支持纯RDB客户端读取
   - 支持纯AOF恢复
```

## 4. 主从复制与持久化

### 常见陷阱

```conf
# 错误配置示例
# 主节点：关闭持久化 + 开启自动重启
appendonly no           # 关闭AOF
save ""                 # 关闭RDB
# 主节点宕机后自动重启，数据全部丢失！
# 从节点也会清空数据同步！
```

### 正确做法

```conf
# 推荐配置
# 主节点：开启持久化
appendonly yes
appendfsync everysec

# 或者至少开启RDB
save 900 1
save 300 10

# 如果主节点压力不大，可以always
appendfsync always
```

### 主从复制流程

```
┌─────────┐                    ┌─────────┐
│ Master  │  BGSAVE            │  Slave  │
│         │ -----------------> │         │
│  内存    │  RDB文件           │  加载RDB │
│         │ <----------------- │         │
│         │  增量命令           │  接收命令 │
└─────────┘                    └─────────┘
```

## 5. 性能对比与选择

### 对比总结

| 特性 | RDB | AOF | 混合持久化 |
|---|---|---|---|
| 文件格式 | 二进制 | 文本命令 | 二进制+命令 |
| 文件大小 | 紧凑 | 膨胀 | 中等 |
| 恢复速度 | 快 | 慢 | 快 |
| 数据安全性 | 低 | 高 | 高 |
| 性能影响 | fork开销 | 磁盘IO | 中等 |
| 压缩 | 支持 | 无 | 支持 |

### 选择建议

#### 优先使用RDB

```markdown
场景：
- 缓存场景，允许少量数据丢失
- 数据集很大，关心恢复速度
- 追求最佳性能
- 可以接受fork开销
```

#### 优先使用AOF

```markdown
场景：
- 对数据完整性要求高
- 作为主数据库使用
- 可以接受一定的性能损失
- 需要实时持久化
```

#### 推荐混合持久化

```markdown
场景：
- Redis 4.0+ 版本
- 既要快速恢复，又要数据安全
- 最佳平衡选择
```

### 配置示例

```conf
# 生产环境推荐配置
# 混合持久化
appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec
aof-use-rdb-preamble yes

# 自动重写
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

# 加载配置
aof-load-truncated yes
aof-use-rdb-preamble yes

# RDB备份（额外备份）
save 900 1
save 300 10
save 60 10000
```

## 6. 故障恢复流程

### 使用RDB恢复

```bash
# 1. 确保RDB文件在正确目录
ls /var/lib/redis/
# dump.rdb

# 2. 启动Redis
redis-server /etc/redis/redis.conf

# 3. 验证数据
redis-cli KEYS "*"
```

### 使用AOF恢复

```bash
# 1. 确保AOF文件在正确目录
ls /var/lib/redis/
# appendonly.aof

# 2. 检查AOF文件完整性
redis-check-aof --fix /var/lib/redis/appendonly.aof

# 3. 启动Redis
redis-server /etc/redis/redis.conf

# 4. 验证数据
redis-cli KEYS "*"
```

### AOF文件损坏处理

```bash
# 1. 备份损坏的文件
cp appendonly.aof appendonly.aof.bak

# 2. 修复文件（移除损坏的命令）
redis-check-aof --fix appendonly.aof

# 3. 检查修复结果
# 如果使用 --fix，可能丢失部分数据
# 考虑使用 --fix --truncate 会更激进

# 4. 启动Redis并验证
redis-server /etc/redis/redis.conf
redis-cli KEYS "*"
```

## 7. 常见面试题

**Q1：RDB和AOF的区别是什么？**

> 参考答案：RDB是定时生成数据快照，适合备份和灾难恢复，但可能丢失最后一次快照后的数据；AOF是记录所有写命令，可以提供更好的数据安全性，但文件较大，恢复速度较慢。Redis 4.0+支持混合持久化，结合两者优点。

**Q2：什么是Copy-On-Write？**

> 参考答案：fork()创建子进程时，父子进程共享同一份物理内存，只有当某进程修改数据时才复制对应的内存页。RDB使用BGSAVE时利用这个机制：子进程遍历内存生成快照，父进程继续处理请求，修改的数据会被复制出去。这样避免了fork时复制整个内存空间的开销。

**Q3：AOF重写为什么需要缓冲区？**

> 参考答案：AOF重写过程中，父进程继续接收写请求，这些新命令不仅写入旧AOF文件，还会写入AOF重写缓冲区。当子进程完成重写后，父进程将缓冲区的命令追加到新AOF文件，然后原子替换旧文件。这样确保重写期间的新命令不会丢失。

**Q4：主节点可以关闭持久化吗？**

> 参考答案：如果主节点使用主从复制架构，且从节点开启了持久化，可以考虑关闭主节点的持久化来提升性能。但要注意：1）如果从节点也没开启持久化，主从切换时会丢失所有数据；2）如果开启自动重启（config set requirepass），主节点重启后数据为空，从节点也会同步空数据。

**Q5：如何选择持久化策略？**

> 参考答案：需要根据业务场景选择。如果作为缓存，可以只使用RDB；如果作为主数据库，要求数据不丢失，推荐开启AOF；如果使用Redis 4.0+，推荐混合持久化。everysec是性能和安全的良好平衡点。
